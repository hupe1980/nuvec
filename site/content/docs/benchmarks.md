nuvec's performance target is MLX on the same machine. Every number here comes from one command in the repository, `just bench-parity`, which runs both engines on the same Mac on the same day and reports losses as well as wins. The latest record, with every sample: [0.4.0, M4 Pro 48 GB (JSON)](/nuvec/benchmarks/0.4.0/m4-pro-48gb.json). Each record is validated against its [schema](/nuvec/benchmarks/parity-record-v1.schema.json), and [index.json](/nuvec/benchmarks/index.json) lists all of them.

## Method

- **Same work.** Both engines get the same mlx-community checkpoint and the same token ids, written once from mlx-lm's tokenizer. Decoding is greedy, and the end-of-sequence token is ignored, so every run generates its 128 tokens.
- **Fresh processes.** Every measurement runs in its own child process, and the engines alternate (nuvec, mlx-lm, nuvec, mlx-lm). Cells show medians; the record keeps every sample.
- **Ratios** are oriented so that above 1.00× favours nuvec: speeds are nuvec / mlx-lm, and times and memory are mlx-lm / nuvec. ⚠️ marks a speed or time cell below the 0.98× gate (run-to-run spread is about ±2%). The goal is 1.0×.
- **Prefill** is prompt tokens over the time to the first token. **Decode** is the tokens after the first over the time they took. The prefill geometric mean leaves out the 25-token rows, which mostly measure the first token.
- **Peak memory** has one definition. For nuvec it is `MemoryStats::peak_with_mapped`: the allocator high-water mark plus mapped files, counted whole. For mlx-lm it is `mx.get_peak_memory()`, which includes the weights it copied. mlx-community checkpoints have unaligned tensors, so nuvec reads them into memory (in parallel, without mapping them); aligned files are mapped without a copy. Each phase runs in a fresh process. The record also keeps nuvec's allocator peak, active and mapped bytes, and the OS peak resident size of both processes.
- **Load** is the time from the start of `load` to a ready model and to the first token of a 16-token prompt: one priming run, then three samples. Cold load needs `sudo -n /usr/sbin/purge` without a password (add a sudoers rule for `/usr/sbin/purge`); without it, cold cells stay empty.
- **Concurrency** serves 1, 4 or 8 prompts of 512 tokens together and generates 128 tokens each: nuvec's `Batcher` against mlx-lm's `BatchGenerator`. "Same tokens as alone" checks nuvec's batched output against each request generated by itself.

## Results: 0.4.0

Apple M4 Pro, 48 GB, macOS 26.6.2; nuvec 0.4.0, mlx 0.32.4, mlx-lm 0.32.2; 2026-10-23; no swap in use.

The geometric means are **decode 1.02×, prefill 1.00×, time to first token 1.01× at 2,048 tokens and 0.98× at 32K and 64K, warm load 1.63×, peak memory 1.02×, and concurrent serving 1.02× / 0.99× / 0.99× at 1 / 4 / 8 requests.**

## Earlier results

0.3.0 (2026-10-21) used a hand-made table. Its memory column used an older definition (the allocator peak without mapped files), and its prefill geometric mean (1.05×) included the 25-token rows. On the same day as the 0.4.0 record, the 0.3.0 and 0.4.0 `bench` binaries, run back to back, decode Qwen3-30B-A3B at the same speed (within 0.3%).

## Kernels

`bench-gemm`, `bench-quant`, `bench-fast` and `bench-compile` run the same kernels in nuvec and MLX with the same method: sustained asynchronous bursts after a warm-up, best of three, programs alternating. Measured with nuvec 0.2 on 2026-10-20:

- Quantized products at language-model shapes, dense (961 × 2048 × 8192) and mixture-of-experts gathers (7,688 rows over 256 experts): 1.00–1.02× MLX's time.
- Prefill attention in bfloat16 (2,048 and 3,841 keys, grouped-query heads): 0.98–1.02×.
- Quantized products of 4–12 rows (speculative verification): 12–22% faster than MLX's per-row kernel, through nuvec's own few-row kernel.
- Decode attention in half precision with keys streamed from memory: about 9% slower than MLX with the same kernel.

## Run them yourself

The benchmarks need [uv](https://docs.astral.sh/uv/), which installs the pinned MLX, and the models in your Hugging Face cache:

```sh
just bench-parity                                  # every section, cached roster models
just bench-parity mlx-community/Qwen3-8B-4bit --sections decode,ttft
just bench-parity --resume --budget 540            # continue a long run in steps
just bench-validate                                # check records against the schema
just bench-compare base.json candidate.json        # fails on a ratio drop above 2%
just bench-quant gqmm                              # kernel benchmarks take a name filter
```

Swap in use makes the numbers noisy. Each record stores the swap in use at its start, and the tables above were taken without swap.
